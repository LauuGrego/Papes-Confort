Flujo de Subida (GesCom → Web)
Middleware lee tablas de artículos, stock y precios del MySQL local cada 1 minuto
Compara con estado anterior mediante hash MD5 por registro
Solo si hay cambios, hace POST al endpoint /api/sync/products con API Key
La API actualiza el catálogo en PostgreSQL
Flujo de Pago — Tarjetas (débito y crédito)
Cliente elige pagar con tarjeta en el checkout
Se redirige al checkout de MercadoPago (procesamiento externo y seguro)
MercadoPago dispara webhook a /api/webhooks/mercadopago
API verifica la firma HMAC-SHA256 del webhook
Si pago aprobado: orden cambia a "Pagado" automáticamente
Se envía email de notificación a Ale con detalle del pedido
El dinero queda acreditado en la cuenta de MercadoPago de Ale para retirar a su CBU
Flujo de Pago — Transferencia bancaria
Cliente elige transferencia en el checkout
El sistema muestra el CBU/alias de la cuenta bancaria activa configurada por Ale
La orden queda en estado "Pendiente confirmación"
Cliente realiza la transferencia por su cuenta
Ale verifica la acreditación en su banco y confirma manualmente desde el panel
La orden pasa a "Pagado" y se dispara el email de notificación
Flujo de Bajada (Web → GesCom, Opción A)
Al confirmar el pago (automático por webhook o manual por transferencia)
La web envía email a Ale con el detalle completo del pedido
Ale ingresa al GesCom, carga el cliente, el producto y emite la factura
En el próximo ciclo del middleware, el stock actualizado baja a la web

5. Estándares de Seguridad
Marco de referencia: OWASP Top 10
A01 — Control de Acceso Roto
Cada endpoint valida el JWT y el rol antes de ejecutar lógica
Middleware de autorización centralizado: requireAuth(role: 'admin' | 'superadmin')
Los endpoints de sincronización de GesCom usan API Key en header X-Sync-Key, nunca en URL
Las credenciales del panel admin no se reutilizan para la API de sincronización
Las cuentas bancarias solo pueden ser modificadas por el rol admin o superadmin
A02 — Fallos Criptográficos
Passwords hasheados con bcrypt (factor de costo 12)
JWTs firmados con RS256 (clave asimétrica)
HTTPS obligatorio en producción
Variables sensibles solo en variables de entorno, nunca en el código
CBU/alias de cuentas bancarias almacenados cifrados en la base de datos
A03 — Inyección
Todo acceso a base de datos a través de Prisma ORM con queries parametrizados
Prohibido construir queries con concatenación de strings
Validación de inputs con Zod en todos los endpoints
Sanitización de datos antes de guardar
A05 — Mala Configuración de Seguridad
Headers de seguridad con Helmet.js
CORS configurado con lista blanca explícita
Modo debug deshabilitado en producción
Logs de errores sin exponer detalles internos al cliente
A07 — Fallos de Autenticación
Rate limiting en login: máximo 5 intentos por IP cada 15 minutos (Redis)
Tokens JWT con expiración corta (15 min) + refresh token (7 días)
Logout invalida el refresh token en Redis
Sesión de admin con timeout automático por inactividad
A08 — Fallos de Integridad (Webhooks)
Verificación de firma HMAC-SHA256 en webhook de MercadoPago
Verificación de IP de origen del webhook
Idempotencia: cada webhook tiene ID único, si ya fue procesado se ignora
A09 — Logging y Monitoreo
Logs estructurados en JSON con Winston
Logs de acceso al panel con timestamp, IP y acción realizada
Logs de sincronización GesCom
Logs de confirmaciones manuales de transferencias (quién confirmó y cuándo)
Nunca loguear passwords, tokens ni datos bancarios completos
Seguridad del Middleware GesCom
Usuario MySQL gescom_reader con solo permisos SELECT en las tablas necesarias
API Key de sincronización distinta a cualquier credencial del panel
El middleware valida el certificado HTTPS del servidor

Ciclo de sincronización de datos (cada 1 minuto)
Hay dos estrategias según lo que se encuentre en el relevamiento del Sprint 1.1:
Estrategia A — Si GesCom tiene columna fecha_modificacion (ideal):
1. Guardar localmente la fecha del último sync exitoso
2. SELECT codigo, descripcion, precio, stock, marca FROM articulos
   WHERE fecha_modificacion >= :ultima_sincronizacion
3. Solo se procesan los artículos que cambiaron → mínimo trabajo
4. Construir payload, aplicar safety_stock, POST a la API
5. Si OK → actualizar fecha de último sync
Estrategia B — Si GesCom NO tiene columna de fecha (fallback):
1. SELECT codigo, descripcion, precio, stock, marca FROM articulos (todos)
2. Para cada artículo:
   a. Calcular hash MD5 del registro (codigo+precio+stock+marca)
   b. Comparar con hash guardado en sync-state.json
   c. Si igual → saltar. Si distinto o nuevo → agregar a la lista de cambios
3. Solo enviar los artículos con cambios detectados
4. Si OK → actualizar sync-state.json con los nuevos hashes
Flujo común a ambas estrategias:
- Aplicar safety_stock: stock_visible = max(0, stock_gescom - safety_stock)
- POST /api/sync/products con API Key en header X-Sync-Key
- Si falla → reintentar hasta 3 veces con backoff exponencial (1s, 2s, 4s)
- Registrar resultado en sync_logs
Sincronización de imágenes con chokidar (en tiempo real, no polling)
En lugar de un cron que repasa el directorio cada N minutos calculando MD5 de miles de archivos, se usa chokidar que reacciona a eventos del filesystem. Esto elimina el trabajo innecesario sobre el disco de Ale cuando no hay cambios.
Convención de nombres en GesCom:
  1234567.jpg      → imagen principal del artículo con SKU 1234567
  1234567_1.jpg    → segunda imagen
  1234567_2.jpg    → tercera imagen
Al arrancar el middleware:
1. chokidar.watch(IMAGES_PATH) inicia el watcher
2. Al detectar evento 'add' (archivo nuevo):
   a. Extraer SKU del nombre (primeros 7 caracteres)
   b. Extraer orden del sufijo (_1, _2, etc.)
   c. Leer el archivo como buffer
   d. POST /api/sync/images con archivo + SKU + filename
   e. La API sube a Cloudflare R2 y guarda la URL en product_images
   f. Si falla → reintentar hasta 3 veces con backoff, luego loguear
3. Al detectar evento 'change' (archivo modificado):
   a. Mismo flujo que 'add', la API actualiza la URL existente
4. Al detectar evento 'unlink' (archivo eliminado):
   a. Notificar a la API para marcar la imagen como inactiva
5. Registrar cada evento procesado en el log
Ventaja: No se calcula ningún MD5 en disco. chokidar usa los eventos nativos del OS (FSEvents en Mac, inotify en Linux, ReadDirectoryChangesW en Windows) para detectar cambios al instante sin polling.
Ciclo de sincronización de marcas
Las marcas se sincronizan dentro del ciclo de productos. El middleware extrae el campo marca de cada artículo y lo incluye en el payload. La API del e-commerce es la responsable de hacer el upsert en la tabla brands (crear si no existe, linkear al producto).
Manejo de errores y resiliencia
Si MySQL de GesCom no está disponible (PC apagada o GesCom cerrado): el cron simplemente loguea el error y espera al próximo ciclo. No crashea.
Si la API del e-commerce no responde: reintentos con backoff exponencial. Después de 3 fallos, loguea y espera al próximo ciclo.
Si una imagen no se puede leer (archivo bloqueado por GesCom): la saltea y sigue con las demás.
Archivo de estado local (sync-state.json): guarda los últimos hashes conocidos. Si se corrompe o borra, el próximo ciclo re-sincroniza todo desde cero (costoso pero seguro).
